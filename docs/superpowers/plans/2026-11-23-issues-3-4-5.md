- JSON frames remain limited to 65,536 bytes. Unknown display versions fall back safely.
- Native and async questions use the same existing parsed/validated form.

## Shared encrypted contract

A new phone requests details with `{type:"list",details:true}`; old `{type:"list"}` remains valid. The desktop sends an authoritative inbox snapshot, followed by one bounded `{type:"question",requestId,display}` message per live authorized request. Only opted-in connections receive question/proposal messages. This avoids overflowing a single inbox frame when several forms are pending. Optional inbox `session` is a bounded display name; `question` is the actual question excerpt, not an async title. No paths, identifiers or capability URLs are used as session-name fallbacks.

```typescript
type QuestionDisplay = {
  v: 1;
  context: string;
  fields: Array<{
    id: string;
    label: string;
    kind: "single" | "multi" | "text";
    required: boolean;
    description?: string;
    other?: boolean;
    inputType?: string;
    placeholder?: string;
    options?: Array<{ id: string; label: string; disabled: boolean }>;
  }>;
};
```

Field and option IDs are generated positional identities, independent of display labels and native submission values. Hidden values and capability tokens are excluded. Maximum 32 fields, 256 options per field, 49,152 UTF-8 bytes per display, 8,192 characters per text field/label, 128 characters for session. Disabled choices are included and visibly marked unavailable. The display is read-only. Missing/unsupported metadata yields an explicit summary-only fallback. Malformed metadata fails safely without making cached choices actionable. On each inbox reconciliation invalidate old detail until matching fresh metadata arrives. Reject orphan details. Clear request-specific details/proposals on retirement, disconnect and request switching.

Optional `{type:"proposal",requestId,text}` carries only an actual validated voice proposal's human-readable summary (maximum 8,192 characters), never invented transcript-derived choices. Empty text clears the proposal. Receipt is not confirmation or submission.

## Retirement wakeup contract

Add desktop-authenticated `POST /v1/invalidations` with exactly `{deviceId,requestId}`. Send the same opaque FCM data `{requestId}` as invitations; no event type or private preview. Use a distinct bounded deduplication namespace so an earlier invitation cannot swallow retirement. The desktop captures the authorized audience before deleting a request, and invokes `SecureDesktop.invalidate(deviceId,requestId)` on authoritative native/async retirement and accepted completion. Python helper operation is `invalidate`.

Android treats every accepted wakeup as a synchronization hint, including replayed known IDs; it never treats a push as authoritative cancellation/submission. Persist closed/seen/silenced lifecycle state. Keep generic pending-sync UI until encrypted reconciliation; do not ring from stale cache. Reconcile in an OS-permitted background job on wakeup, network recovery and stale actions. Offline/delayed delivery removal is eventual, not instantaneous. Close withdrawn calls, cancel the exact notification, retain unrelated requests.
