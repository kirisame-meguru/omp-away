# omp-away: answer a built-in Ask by voice

The Android phone is another way to answer the original desktop Ask, not another agent, form, or authority to execute work. The desktop is authoritative for request validity, the conversation, and Codex login. The public relay delivers opaque invites and forwards encrypted streams. No phone traffic to OpenAI, public omp relay, SIP, or Tailscale.

## Three owners

- `plugin/`: desktop extension, loopback Collab responder, authenticated endpoint, voice/media bridge. Use a control room already aimed at the plugin's loopback relay **before** Ask opens; never repurpose a user's existing remote room. The control link never leaves the desktop. Accept only confirmed form answers, never prompt/abort/agent control. The first valid desktop or guest submission wins inside built-in Ask. No core edits, private UI instance manipulation, or replacement forms.
- `relay/`: the public HTTPS/WSS endpoint `away.example.com`, provisioned on the authorized host. Holds installation routing, FCM tokens, and opaque pending identifiers. Never receives decrypted questions, decisions or audio. Generic FCM notification; no field data, phone bearer token or key in a notification or URL log.
- `android/`: paired native Android app with a pending inbox, generic invite, audio input/output, Not now, hangup and answer flows. Only the relay and Google services are network dependencies of the handset. End-to-end identity verification with matching emoji codes and persistent pins; changed keys block calls until verified again.

## Decisions

Normal routing shows Ask on the desktop. Optional escalation has an independent configurable timeout and can be disabled. `/away` rings immediately. Neither an escalation nor FCM delivery resolves anything. Require native `ask.timeout=0` for the keep-pending contract. Declining suppresses future ringing for that request. Hanging up or a dropped connection leaves it pending; a cancelled desktop request disappears from the inbox.

The coding session supplies the native question and bounded, silent task context. The desktop-authenticated `gpt-live-1-codex` call answers ordinary questions directly from that context; it must not promise a second desktop answer. A person may propose an answer in their own words. Only caller evidence, native form validation and the current request can establish the immutable canonical draft. Codex may read those choices back naturally and ask whether to submit them. Check the meaning against the complete validated draft, not the wording of the whole assistant utterance. Real handset playout must finish first; a separate, subsequent, unambiguous spoken affirmative (a plain “yes” is sufficient) submits that same pending Ask at most once. There is no required preamble, recited phrase or spoken challenge. An early yes, interruption, correction, changed value, stale request or missing playback proof must not submit. Pairing and internal request/playback identifiers are protocol machinery, never spoken call steps.

### Approved readback coordination

The user approved checking an existing realtime readback before requesting another. This replaces the earlier uncertain desktop-only selection. The following is the implementation contract, not a claim that the current runtime already satisfies it.

- **Canonical owner:** `decisions/call.ts` retains the caller-derived immutable draft and its caller-turn owner. Assistant observations never create, patch or complete that draft. Draft issuance alone no longer enables confirmation.
- **Speech observation:** `media/session.ts` retains bounded assistant output for the current caller turn, with an opaque response ID, ordered provider coordinates, complete transcript and audio-delivery boundary. Group contiguous final fragments without deleting captions or caller words. Reject ambiguous, overlapping, regressing, interrupted or unscoped evidence. A late final from an older response cannot attach to a newer caller turn.
- **Scheduling:** after a canonical draft is ready, runtime first inspects or waits for the current response. It does not request another readback while that response is still playing or being verified. A complete matching readback is reused. Missing, incomplete or mismatched readbacks require one corrected desktop request after existing output finishes; that requested readback passes the same checks. If output completion cannot be established, fail closed instead of speaking a competing request.
- **Independent verification:** a tool-free `verify` side turn interprets only the candidate readback against the native form, without a previous draft or caller-derived answers supplied as completion hints. Require explicit evidence for every editable field; reject contradictions, conditional alternatives, missing values and more than one Submit question. Validate the returned field/evidence structure with native draft validation, then compare all canonical values to the already validated caller draft. A model's bare assertion that the readback matches is insufficient.
- **Physical playback:** after all corresponding PCM has been delivered in order, runtime sends the existing opaque `mark` control. The existing handset `played` response follows its strict AudioTrack presentation-timestamp fence. Bind that acknowledgment to the active device, request, caller-turn owner, response and immutable draft; unknown, repeated and obsolete marks have no authority. Sending a mark, receiving a transcript or seeing output quiet alone is not playback proof.
- **Confirmation snapshot:** at caller onset, capture only a draft and complete response already known before that physical onset, with its playback acknowledgment also preceding onset. Semantic verification may still be running for those immutable observations; a later pure affirmative can await that result, but cannot acquire later transcript, playback or draft evidence. Submit only if verification succeeds and the request, draft and utterance remain current. An onset before playback, a qualifier, cancellation, correction, stale result or newer utterance must not submit.
- **Interruption and cleanup:** revoke current eligibility at every caller onset or interrupt. Preserve the last validated proposal across aborted classification, but never let aborted work mutate it. Bound response storage and verification work; cancel obsolete work on replacement, hangup or request retirement. Preserve the approved 1500 ms live-microphone silence boundary and fresh-capture safeguards; do not mute microphone input or hide output.
- **Debug isolation:** run current helper code with its own private state, identity, local listeners and relay control endpoint. Do not reuse production gateway state or connect competing helpers to its relay control socket. Do not restart unrelated desktop sessions. A loopback TLS relay fixture supports debugging but does not prove production FCM or physical-phone behavior.

Verification must cover a matching spontaneous readback without a second request; wrong/missing/negated fields; a duplicate Submit question; fragmented and late output; mark-before-audio and stale/replayed marks; confirmation during playback; delayed verification with immutable onset evidence; qualification, correction and cancellation while verification runs; unknown context; interrupted readbacks; native validation failures; and exactly one native submission. Final acceptance requires the real OnePlus microphone, speaker, visible captions and native Ask result, not only synthetic transcript injection or helper readiness.
