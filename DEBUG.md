# Public relay: install and diagnose

The relay is an HTTP/1.1 backend on **127.0.0.1:8787 only**. A host-managed TLS reverse proxy exposes `https://away.example.invalid:443` and upgrades `/v1/control`, `/v1/phone`, and `/v1/tunnels/{connectionId}` to WSS. Never expose the backend, desktop or Collab port. Outer TLS terminates at the proxy; the independent pinned TLS stream terminates only on desktop and handset. A valid routing bearer is not a paired identity.

## Before installation

- Authorized host operator only: inventory existing DNS, TCP listeners, virtual hosts, firewall, systemd units, certificate automation and proxy configuration. Reserve the loopback port and service/vhost names; stop on a collision. Do not bind a second public listener or change another service's vhost. Confirm expected A/AAAA records and coverage of **both** address families before publishing DNS.
- Enable Firebase Cloud Messaging HTTP v1 on `omp-away`. Bind the dedicated service identity to a project-level custom role containing **only** `cloudmessaging.messages.create`. Do not grant Editor, Firebase Admin, database access, or service-account key creation. Prefer a dedicated workload identity; shared instance metadata is not a service-specific identity. Do not use a developer login as ADC. The SDK requests the `firebase.messaging` OAuth scope. Allow DNS, certificate validation and approved Google token/FCM endpoints; the relay never needs OpenAI, desktop or phone inbound ports.
- Build from the reviewed relay repository with Go 1.26+, committed dependency sums and the target OS/architecture. For example, from `relay/` on Linux: `go test -race ./...` then `CGO_ENABLED=0 go build -mod=readonly -trimpath -o /tmp/away-relay ./cmd/away-relay`. Install the binary root-owned mode 0755 at `/usr/local/lib/omp-away/away-relay`. Keep the previous binary/unit/vhost revision for rollback. No source tree or Go toolchain is needed in the runtime service.

## Secrets and service

1. On the target, `/etc/omp-away/desktop.token` and `/etc/omp-away/firebase-adc.json` are already provisioned root-private. **Do not read them into a terminal, regenerate them, or change their ACLs.** The desktop must have its matching bearer through its protected local secret store. `AWAY_DESKTOP_TOKEN_FILE` is a **path**, not bearer text; its credential is exactly 32 bytes encoded as unpadded base64url (optional final newline).
2. Install `deploy/away-relay.service` at `/etc/systemd/system/away-relay.service`, root-owned mode 0644. `DynamicUser=yes` supplies a dedicated non-root service account. `StateDirectory=away-relay` supplies the private directory `/var/lib/away-relay` (mode 0700). `AWAY_STATE_DIR` selects that directory; `AWAY_LISTEN` must be a literal loopback address and nonzero port. If the port changes, change the proxy too.
3. The unit uses `LoadCredential=desktop-token:/etc/omp-away/desktop.token` and `LoadCredential=google-adc:/etc/omp-away/firebase-adc.json`. Systemd reads the sources as root and exposes read-only service-scoped copies through `%d`. `GOOGLE_APPLICATION_CREDENTIALS=%d/google-adc` selects the dedicated ADC; do not put its contents in the unit or environment. On a **different** host using a dedicated attached workload identity, remove just the `google-adc` credential directive and `GOOGLE_APPLICATION_CREDENTIALS` setting from the unit. Never accept credential configurations supplied by clients.
4. Validate the unit with `systemd-analyze verify /etc/systemd/system/away-relay.service`; then `systemctl daemon-reload` and `systemctl enable --now away-relay.service`. Check `systemctl is-active away-relay.service`, `ss -ltn` (only loopback for this backend), and `curl --noproxy '*' -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8787/healthz` (200, empty body).

## TLS and public health

`deploy/away-relay.nginx.conf` is a dedicated additive example for an existing nginx `http` context. Do not replace `nginx.conf`. Use the host's existing proxy and ACME/certificate renewal system; provision a public CA chain for the hostname first. Adapt only the matching certificate paths, address families and upstream port. If AAAA is published, add the host-compatible IPv6 listen directive to the dedicated vhost. Do not add an HTTP-to-HTTPS redirect as an authenticated endpoint. Disallow URL/auth/header/body logging and packet debugging on this vhost, upstream, WAF and monitoring services; secrets belong in Authorization or JSON bodies, never URLs. Do not enable caching, compression of WS frames, or upstream retries. The peer at loopback is not an authenticated phone identity; do not trust forwarded headers for routing.

Stage the dedicated vhost, run `nginx -t` (or the host proxy's config validator); only on success reload the existing service normally. Verify unrelated health checks are unchanged. From an external client:

```sh
curl --proto '=https' --max-redirs 0 -fsS -o /dev/null -w '%{http_code}\n' https://away.example.invalid/healthz
curl --proto '=https' --max-redirs 0 -sS -o /dev/null -w '%{http_code}\n' -X POST -H 'Content-Type: application/json' --data '{}' https://away.example.invalid/v1/enrollments
```

Expect **200**, then **401**. Never use `-k`, verbose auth traces, or share real request URLs containing IDs. For rollback, remove/restore only this vhost, revalidate and reload, stop this service and restore the prior reviewed binary/unit. Do not delete its state directory unless deliberately revoking all registrations.

## Behavior and failure boundaries

- `routes.db` (0600) stores random device IDs, SHA-256 phone bearer digests, recoverable current FCM tokens and a bounded push deduplication ledger. FCM routing requires recoverability: protect the volume and offline backups, including old database pages. Enrollment tickets are SHA-256 indexed **in memory only**; expire in 10 minutes, consumed once, invalidated on restart. The desktop bearer is compared by digest. Capacity: 32 outstanding tickets, 256 lifetime device registrations, 4096 recent invite reservations. There is no public admin endpoint. To revoke **all** installed routes, stop the service, securely isolate/retire its database and backups, rotate the desktop token, restart, then re-pair each device. Revoke exposed Google credentials independently. Deleting a relay route is not an inner-key rotation.
- A wake is an Android high-priority **data-only** FCM HTTP v1 message (45 s TTL) with precisely one key: `requestId`. No notification payload, question, audio, capability or login. Android renders the visible generic notification with its native actions. A 204 means accepted/coalesced, **not** delivered, seen or answered. Persist-before-send suppresses duplicate `(deviceId, requestId)` for 10 minutes across restarts. Concurrent callers share an outcome. After an ambiguous network failure/crash a send may be lost: return failure and suppress retry for the remaining window rather than ring twice. The private inbox remains authoritative. FCM's typed `UNREGISTERED` or `INVALID_ARGUMENT` for this fixed valid payload clears only the exact token used for that send; general HTTP 400s and permission errors never clear a token.
- 400/415: noncontract input (including unknown/duplicate keys, non-JSON, query strings or browser Origin). 401: missing/wrong bearer or expired/reused ticket. 404: no route. 409: no FCM registration or occupied slot. 410: FCM unregistered the token; the handset must upload a current token. 429: bounded capacity/rate. 502/503: push outcome unknown, backend unavailable, or no control connection. Resolve credentials, connectivity and notification permission without dumping bodies or IDs. Database/disk errors fail closed.
- One desktop control, at most 16 duplex tunnels, one per device. Pending attachment lasts 15 s. Sockets use a 25 s ping and 10 s write deadline, two-hour absolute session limit, 128 KiB max binary message, 256 messages/s and 1 MiB/s per direction with limited bursts. A failed/disconnected counterpart or lost control epoch cancels both sides. The relay holds at most one frame per direction; TCP/WS backpressure handles the rest. The backend also caps total connections, concurrent handlers, request JSON, headers, and both setup and push rates. Global limits are for this single-operator deployment; use the proxy's per-client limits to protect availability.
- Health is liveness only. Do not claim pairing, FCM delivery, inner pin protection or working calls from health/FCM acceptance. Use the approved real handset and desktop workflow for deployment evidence. Logs must contain only categorical service status; never capture live credentials, tokens, decrypted content or session transcripts.
